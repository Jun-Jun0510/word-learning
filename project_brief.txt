# 役割
あなたは技術系プロダクトのリード。以下のアイデアを、要件定義 → 設計 → 動くプロトタイプまで一緒に作る。

# 作りたいもの
英語の論文・技術記事を「翻訳せずに読む」ための、事前単語学習アプリ。
既存の翻訳ツールは全文を訳してしまい学習にならない。そうではなく、読む前に
PDF/URL/テキストを読み込ませ、その文書に出てくる単語を「一般的な難易度」ではなく
「その読者にとっての危険度」でレベル分けして提示し、10〜15分で予習できる状態にする。

# 中核仮説（ここが差別化点。妥当性も批判的に検証すること）
単語レベルを以下で定義する:
- L1 一般語: 一般英語コーパスでも高頻度。除外。
- L2 明白な専門語: 見た目で専門語と分かる（eigenvalue, holonomic 等）。
  辞書を引けば済むので中優先。
- L3 危険語【最優先】: 見た目は日常語だが、その分野で特殊な意味を持つ語。
  例: kernel, regular, sample, admissible, degenerate, novel, tight,
      sound, plant, gain, observer, dense, sharp
  → 読者は「知ってるつもり」で誤読する。ここを潰すのが最大の学習効果。
- L4 略語・記号: FOC, PMSM, MPC 等。文書内で定義されていれば抽出。

L3抽出の初期案: 一般英語コーパス（wordfreq / SUBTLEX 等）で高頻度なのに、
対象分野コーパス（arXiv cs.RO / cs.LG 等）で相対頻度が突出している語を
tf-idf的に検出する。この案が妥当か、より良い手法（分野間の語義差、
collocationの違い、LLMによる語義判定等）があるかを必ず検討し、比較して結論を出せ。

# 進め方（フェーズごとに必ず俺のレビューを挟む。勝手に次へ進むな）
Phase 0: 要件定義
  - まず俺に質問しろ。曖昧な点・前提の確認を最大10個、優先度順に。
    俺が答えるまで実装に着手するな。
  - その後 docs/requirements.md に ユーザーストーリー / スコープ / 非スコープ /
    成功指標 を書く。
Phase 1: 設計
  - docs/architecture.md に データフロー / モジュール分割 / 技術選定と理由 /
    リスク を書く。図はMermaidで。
  - L3判定アルゴリズムは docs/algorithm.md に単独で切り出し、
    「精度をどう測るか」（評価用正解セットの作り方含む）まで書く。
Phase 2: プロトタイプ
  - 最小構成で「テキストを貼る → レベル分けされた単語リストが出る」まで動かす。
  - arXivのabstract 3本程度を実際に流し、出力を俺に見せて議論する。

# チーム編成
サブエージェントで並列化してよい。想定:
  - requirements-agent: ユーザーストーリー、競合調査
    （Readlang / LingQ / Anki / Yomitan / DeepL との差分を明確に）
  - algorithm-agent: L3抽出ロジックのPoCと精度評価
  - frontend-agent: UI
  - reviewer-agent: 各フェーズの成果物に容赦なく突っ込む役。忖度禁止。
