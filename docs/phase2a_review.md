## 90%は汎化性能ではない
正解セットを凍結した上で5イテレーション改良を回した時点で、この20語は
テストセットではなく検証セットになっている。アルゴリズムはこの20語に適合済み。
したがって現時点で未知語に対する性能を示している数値は precision@50 のみ。

対応:
- 以後、この20語での再現率を「性能が上がった」根拠に使うな。
  設計変更が既存の検出を壊していないかの回帰テストとしてのみ使え。
- Phase 2b のゲート用に held-out セットを別途用意する。俺が10語追加で作る。
  この10語は2bのゲート判定でのみ使い、それまで一切参照するな。形式は同じでよい。
- eval_report.md に「この数値は検証セットに対するもの」と明記しろ。

## 判断1: 話題語混入 → 第3信号への投資は保留

θrr マージンが薄いのは事実だが、Cコーパスが目標の4割の状態での薄さであり、
原理的限界かデータ不足かが切り分けられていない。
SGNS+OP は実装コストが重い。順序は以下:
  1. Cコーパスを目標量まで拡充
  2. 再計測してマージンを確認
  3. それでも robot/controller/simulation が混入するなら第3信号を検討
現時点では robot/controller/simulation の混入を許容する。
ただし予習モードでの実害を減らすため、話題語疑いフラグが立った語は
L3リスト内で視覚的に区別できる形にしておけ(後で消せるように)。

## 判断2: Cコーパスは量の前に構成を決めろ

sound の C側共起が respiratory/music/acoustic という結果を
「コーパスに忠実」で片付けるな。cs.LG には音響系論文が大量にあるので
統計的には正しいが、俺が実際に読むのは manipulation / VLA / sim-to-real 系。
読まない分野の語彙が分野コーパスを支配すると、L3上位が実用と無関係になる。

Cを4割から満たす際、単純にAPIを回すのではなく先にカテゴリ構成を決めろ:
- cs.RO と cs.LG の比率をどうするか
- cs.LG 内で音響・NLP・vision の比率をどう扱うか
- 構成を変えた場合に sound がどう動くかを before/after で見せろ
構成案を出してから収集に入ること。収集後に「やり直し」は時間の無駄になる。

## 判断3: mass の語義単位問題 → Phase 2c ではなく今決めろ

「検出は語単位で足りたが表示では語義単位が必要」は単語帳スキーマに直結する。
語をキーにした1エントリでは多義語を保持できない。さらにステータス
(new/learning/known) も語義ごとに別であるべき
(確率質量は未知だが物理質量は既知、という状態が普通に起きる)。
2b でデータ構造を作ってから直すと作り直しになる。
今スキーマ案を出せ。実装は 2b でよい。

## augmentation の扱い

L2として表示されるなら実害はほぼない。正解セットは凍結を維持し、
これを「既知の不一致」として記録するだけでよい。俺の正解セット側の
誤りである可能性も併記しておけ。セットは書き換えるな。

## greedy の取りこぼし

A側共起が疎という診断は妥当。OpenSubtitles は会話コーパスなので
文脈が薄い語が出るのは構造的な弱点。1/20 なので今は対応不要。
ただし同種の取りこぼしが held-out セットで再発したら A の補強を検討する。
eval_report.md に「A起因の取りこぼし」として分類だけしておけ。
