全体として承認。話題ズレの分離は自分では気づけなかった。replaceGen も筋がいい。

## 1. 話題語ガードの副作用 → 保留でよい。ただし条件2つ

PoC実測後に確定、で合意。ただし「保留」が静かな取りこぼしになる構造は
L1a除外とまったく同じなので、同じ扱いをしろ。

条件a: 話題語疑いプールを破棄せず全て中間データに残し、
       デバッグ出力で「話題語疑いに落ちた語の上位N件」を一覧させろ。
       俺が目視して kernel / sample / dense がここに沈んでいないか確認する。
条件b: 話題語とL3は排他ではない。kernel は分野で話題語かつ語義がズレる。
       replaceGen が閾値を超える語は話題語疑いからL3へ復活する経路を必ず通せ。
       ガードは足切りではなく優先度の減点として実装するほうが安全なら、そうしろ。
       どちらを採ったか algorithm.md に明記すること。

## 2. L3-academic 完全非スコープ → 承認

A-vs-B の語義信号が別途必要という判断に同意。Phase 2 で混ぜると評価が濁る。
正解セットに入れない方針も承認。
ただし Phase 3 で拾う前提は残せ。データ構造上 level に 'L3-academic' を
後から足せる形にしておくこと。実装はするな。

## 3. 暫定値 → precision@50≥60% は承認。L3表示上限は20語に下げる

理由: 予習は10〜15分。30語のL3を消化しつつL2も見るのは時間的に成立しない。
ただし上限値そのものより、超過時の削り方を先に決めろ。
  - 30語出たとき、どの順序で20語に絞るか(スコア順か、出現回数併用か)
  - 削られた10語をユーザーが「もっと見る」で展開できるか
この設計を先に書け。上限値は実測後に調整可能なパラメータにしておくこと。

## 正解セットの形式 → 承認

algorithm.md §6-1 の YAML で進める。20語+負例を数語、俺が書いて渡す。
expected_signal が診断の肝という指摘に同意。
負例は意図的に2種類入れる:
  - 話題語型の負例(robot, controller のように共起は激変するが語義不変)
  - 一般語型の負例(頻度も語義も動かない語)
この2種を分けておけば、話題語ガードの効きと候補プールの効きを別々に測れる。
