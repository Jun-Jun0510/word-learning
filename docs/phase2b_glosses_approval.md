# 判断3件 → 案A採用、L3+L2全語、Haiku開始

## ① 案A(ビルド時全語プリベイク)を採用

実行時が静的配信のままで Phase 0 の (a) の枠内に収まる点を評価する。
APIキー不要・オフライン常時動作という当初要件を壊さずに説明文が手に入る。
キャッシュ方式より優れている。

案B(実行時ユーザーキー)は将来の未収載語対応として温存、で承認。

## ② 範囲は L3+L2 全語($12)

$12 は一回きりのビルドコストとして許容範囲。
L3のみに絞ると、L2(eigenvalue, holonomic 等の明白な専門語)の説明が
永久に欠落する。L2 は「辞書を引けば済む」と Phase 0 で位置づけたが、
説明が既にあるなら引く手間が消える。予習時間の短縮に直結する。

ただし L2 のプロンプトは L3 と分けろ。
L3 は「一般的な意味との対比」が核だが、L2 には対比する一般語義がない。
L2 は「その語が何を指すか」を簡潔に説明するだけでよい。
同じプロンプトで生成すると L2 に無理な対比が付いて品質が落ちる。

## ③ Haiku で開始 → 品質を見て判断

$1 で全語生成し、正解セット+heldout の30語で抜き取り検査する。
判断基準は「一行で刺さるか」であって正確さではない。
Haiku で刺さるなら Sonnet は不要。

品質不足と判断した場合、全語を Sonnet で再生成するのではなく、
L3 のみ Sonnet で再生成する選択肢も検討しろ。
対比が要るのは L3 だけなので、難易度が高いのも L3 だけのはず。

## 生成時の必須要件

1. 俺の3例文(curriculum / disturbance / actor)を few-shot に使え。承認済み。
2. senses.yaml の手書きが常に優先。承認済み。
3. 生成結果は必ずファイルに保存し、差分でレビューできる形にしろ。
   30語の抜き取り検査だけでなく、俺が後から気になった語を確認できること。
4. 生成に失敗した語、または空になった語のリストを別途出せ。
   静かに欠落させるな。

## 抜き取り検査の報告形式

30語について以下を並べて出せ。俺が見て判断する:
  語 / 一般(日本語)/ 分野(日本語)/ 分野(英語)
特に確認したいのは、正解セットで俺が手で書いた general / domain と
生成結果がどれだけ一致するか。乖離があれば、俺の書き方が特殊なのか
生成が弱いのかを切り分けたい。

## その他の修正(1〜3, 5〜7)は承認

出現文の切断が小数点だったこと、判定用分割器を凍結したまま
表示専用分割器を新設した判断、いずれも正しい。
グルーピングの接辞リスト不備(ity/ness/ment)も確定バグとして納得した。
未照合55%の内訳(ストップワード33% + L1a 2.5%)も了解。
UIラベルの修正で対応済みとのことなので問題ない。
