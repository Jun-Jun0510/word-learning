## Q1. 対象分野の初期スコープ
cs.RO + cs.LG の2つを合わせて「1分野」として扱う。eess.SY は非スコープ。
理由: 俺は制御系エンジニアなので plant / gain / observer / regular は既知。
読者を俺に固定する以上、分野コーパスは「俺が知らない側」に寄せるべき。
複数分野の切り替えは初期スコープ外。

## Q2. LLM API利用の可否
(c) ハイブリッドを最終形とするが、Phase 2 は (a) 完全静的で作る。
原則: レベル判定そのものをLLMに投げるな。判定を静的アルゴリズムに置くから
精度を測れるし、そこがこのアプリの中身になる。LLMは語義説明の文面生成のみ。
説明の質が実際に不足すると確認できてから (c) に拡張する。順序を守れ。

## Q3. 「読者」の定義
俺自身に固定。既知語の記録は初期スコープに含める(詳細はQ5・単語帳の項)。

## Q4. 出力に何を表示するか
必須3つ:
  - その分野での意味(英語)
  - 一般的な意味との対比(L3の肝。一行で刺さらないと意味がない)
  - 文書内の実際の出現文を1つ
日本語訳はトグル(デフォルト非表示)。翻訳に頼らないのが目的。
出現回数は内部値として保持し、UIには小さく添える程度。

## Q5. 予習体験の形式
リストを眺めるだけ。フラッシュカードは非スコープ。
各項目にステータス変更を1タップで置く(後述の3値ステータス)。

## Q6. 入力形式の優先順位
Phase 2 はテキスト貼り付けのみ。次点 PDF(pdf.js でブラウザ完結、Phase 3)。
URL取り込みは CORS proxy が要り構成が汚れるので最後。優先度を上げるな。

## Q7. 静的データのサイズ許容量
上限5MB、目標1MB以下。数十MBは論外。
配信すべきは頻度表そのものではなく事前計算の結果だけ。
重い集計はビルド時にNodeスクリプトで回してJSONに焼き、実行時は引くだけにする。

## Q8. 成功指標
最終目的: 対象論文をDeepL等に丸投げせず、英語のまま最後まで読み切れること。
主指標: 読了直後、提示されたL3語を見返して「読中に正しい分野固有の意味で
       解釈できていたか」を自己採点。正答率80%以上。
副指標: 論文3本連続で「丸投げせずに読み切れた = Yes」。
アルゴリズム指標: 手作りの正解セット20語に対しL3検出の再現率70%以上。

注意: 「読中に辞書を引く回数」を指標にするな。予習が効くと誤読への気づきが
増え、確認回数はむしろ増えうる。減るべきは引く回数ではなく、引かずに誤読する回数。
この自己採点を記録するUI(読了後チェック画面)を持たせること。

## Q9. Ankiエクスポート
機能実装は非スコープ。ただしデータ構造はCSV出力可能な形にしておく。
(別途、JSONエクスポート/インポートは Phase 2 必須。後述)

## Q10. フロントエンド技術
React + Vite + TypeScript + Tailwind。
Web系の経験は薄いので、選定理由と初期セットアップを docs に手順として残せ。
状態管理ライブラリは最初から入れるな。useState で足りるうちは足りるはず。

# 追加補足

## 1. レベル定義の再構成(最重要)
L1とL3は対立する2カテゴリではない。「一般英語で高頻度」という同じ入口から
入ってくる同一母集団を、分野側の挙動で割った結果である。
したがって「L1除外」という工程を作るな。まず縦軸(一般頻度)で候補プールを作り、
その中を横軸(分野でのズレ)で割る、という順序で実装しろ。

## 2. コーパス構成は3本
  A: 一般英語コーパス(日常英語。wordfreq / SUBTLEX)
  B: 学術英語コーパス(分野横断の論文英語)
  C: 分野コーパス(cs.RO + cs.LG)

分類:
  L1a  Aで高頻度、BでもCでも突出しない → 非表示
  L1b  Aに対しBで突出、Cでは特に突出しない → 「論文英語」層。表示
       例: denote, yield, respectively, hence, constitute, thereby
  L3   Aで高頻度だが、Cで分布・語義がズレる → 最優先
  L2   Aで低頻度、Cで高頻度 → 中優先
  L4   略語。上記の平面外。Phase 3。

L1bはB由来なので分野を問わず再利用でき、学習効率が最も高い。
Cを切り替えても残る資産として扱え。
「一般頻度の上位N語カット」という閾値方式は廃止する。

## 3. L1除外の検証
L1a判定はL3の取りこぼしを静かに生む。必ず検証しろ。
- L1aは破棄せず「保留」として中間データに全て残す。
- 保留語のうちCで相対頻度が閾値を超えるものはL3候補に復活させる復活パスを通す。
- デバッグ出力として「L1aで落ちた語の上位N件」を一覧できるようにしろ。
  ここに kernel / regular / sample / sound / plant / tight / dense が
  混ざっていれば閾値が誤っている。俺が目視できる形にすること。
- 評価スクリプトでは正解セットの取りこぼしについて「判定ロジックが落としたのか、
  L1a判定が先に落としたのか」を必ず切り分けて報告しろ。
  この切り分けがないと再現率が原因究明に使えない。

## 4. 横軸の測り方(最大の技術リスク)
「分野で挙動がズレる」を頻度比(tf-idf的)で測るのは代理指標にすぎない。
頻度は変わらず語義だけ変わる語(regular=正則, sound=健全)が漏れる。
より直接的な信号は共起語の分布差。sample の隣に来る語は一般英語では
free / blood / take、cs.LG では from the distribution / i.i.d. / minibatch と入れ替わる。
これは通時的意味変化検出(semantic change detection)と同一の問題構造であり、
時代軸を分野軸に置き換えるだけで先行研究が流用できる。必ず調査して比較検討しろ。

## 5. フィルタの原則
文書内の出現回数でL2/L3を足切りするな。1回しか出現しない専門語も必ず出す。
出現回数はソート補助と表示用に持つだけで、抽出の閾値には使わない。

## 6. モード分離
UIを2モードに分ける。混ぜるな。
[予習モード] 読む直前。L3 → L2 のみ。10〜15分で読み始められること。
             L1bはここに出さない。当初設計を死守する。
[単語帳モード] 蓄積した語を後から見る。L3/L2/L1b 全部。
             レベル別・習得状況・出典文書でフィルタできること。

## 7. 単語帳の蓄積
文書を読み込むたびに語が永続DBに積まれる。同じ語が複数文書に出たら
出典を配列で持ち出現回数を加算する(重複エントリを作るな)。
ステータスは3値: new / learning / known。
known は予習モードから消えるが単語帳には残る。
これが「使うほど予習が軽くなる」導線の本体。1タップで変えられること。
保存は localStorage。上限時の挙動を設計しておけ。
JSONエクスポート/インポートは Phase 2 必須。非スコープにするな。
蓄積型にした時点でデータの価値が上がり、消えると全部無価値になる。

## 8. 評価用の正解セット
20語は俺が手で作る。Phase 1 の algorithm.md では
「どういう形式で渡せば評価スクリプトに食わせられるか」を先に定義しろ。
形式が決まり次第、俺が20語を書いて渡す。

# algorithm-agent への検討課題

1. BとCの間に「数学・工学一般」の中間層が存在しうる
   (denote, admissible, bound, converge 等は分野横断だが日常語ではない)。
   B単独で吸収できるか第4コーパスが要るかを実データで判断しろ。
   過剰に分けるな、まず3本で測れ。

2. L3は現状Cに対してのみ定義しているが、B(学術英語一般)に対しても
   同種の語義ズレが存在する(significant=統計的有意, control=対照群,
   argue=主張する, suggest=示唆する)。これらは分野を問わず誤読を生む。
   「L3-academic」として分けるべきかL1bに含めるべきかを検討し結論を書け。
   判断基準は実装の複雑化に見合うかどうか。
